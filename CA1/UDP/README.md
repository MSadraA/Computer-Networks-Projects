# تمرین کامپیوتری ۱ – بخش اول: UDP Pinger

## ۱. معماری برنامه

این بخش از پروژه شامل دو برنامه `ping-server` و `ping-client` است که با استفاده از سوکت‌های UDP پیاده‌سازی شده‌اند.

برای اینکه کدها ساختار منظم‌تری داشته باشند و هر قسمت وظیفه مشخصی را بر عهده بگیرد، برنامه به‌صورت ماژولار طراحی شده است. کلاس‌های اصلی برنامه عبارت‌اند از:

- **`UDPSocket`**: مدیریت عملیات مربوط به سوکت و ارتباط با توابع سیستمی. همچنین با استفاده از تابع `select`، امکان کنترل زمان انتظار برای دریافت اطلاعات فراهم شده است.
- **`MessageParser`**: بررسی قالب پیام‌های دریافتی، استخراج فیلدهای آن‌ها و آماده‌سازی پیام‌ها برای پردازش.
- **`PingStats`**: ثبت زمان رفت‌وبرگشت بسته‌ها (RTT) و محاسبه آمار نهایی، مانند تعداد بسته‌های ارسال‌شده و دریافت‌شده و درصد اتلاف بسته‌ها.
- **`PingServer`**: مدیریت اجرای سرور، بررسی پیام‌های دریافتی و شبیه‌سازی اتلاف بسته‌ها بر اساس احتمال تعیین‌شده.
- **`PingClient`**: مدیریت ارسال درخواست‌های Ping، زمان‌بندی ارسال با استفاده از `steady_clock`، بررسی Timeout و پردازش پاسخ‌های دریافتی. همچنین پاسخ‌هایی که پس از پایان مهلت انتظار دریافت می‌شوند، نادیده گرفته خواهند شد.

## ۲. نحوه کامپایل

برای کامپایل برنامه‌های سرور و کلاینت، ابتدا وارد پوشه `UDP` شوید و دستور زیر را اجرا کنید:

```bash
make
```

پس از اجرای دستور، دو فایل اجرایی زیر ساخته می‌شوند:

- `ping-server`
- `ping-client`

## ۳. ایجاد محیط تست با Tmux

برای اینکه بتوان سرور و کلاینت را هم‌زمان و در یک محیط ترمینال اجرا و مدیریت کرد، دستوری در فایل `Makefile` قرار داده شده است.

با اجرای دستور زیر، محیط تست ایجاد می‌شود:

```bash
make tmux-env
```

این دستور یک نشست جدید در `Tmux` باز می‌کند و صفحه ترمینال را به دو قسمت تقسیم می‌کند. به این ترتیب، می‌توان در هر قسمت دستورات مربوط به سرور یا کلاینت را به‌صورت جداگانه وارد کرد و سناریوهای مختلف را اجرا کرد.

## ۴. سناریوهای تست

برای بررسی عملکرد برنامه، چند سناریوی مختلف در نظر گرفته شده است که هرکدام بخشی از قابلیت‌های سرور و کلاینت را آزمایش می‌کنند.

### ۴.۱. سناریو اول: عملکرد عادی و شبیه‌سازی اتلاف بسته

در این سناریو، سرور با احتمال اتلاف بسته ۲۰ درصد اجرا می‌شود و کلاینت نیز ۵ درخواست Ping ارسال می‌کند.

**دستور اجرا در قاب سرور:**

```bash
./ping-server --port 9000 --loss 0.2 --seed 123
```

**دستور اجرا در قاب کلاینت:**

```bash
./ping-client --host 127.0.0.1 --port 9000 --count 5 --timeout 1000 --interval 1000
```

**نمونه خروجی مورد انتظار کلاینت:**

```text
PONG seq=1 rtt=0.412 ms
TIMEOUT seq=2
PONG seq=3 rtt=0.388 ms
PONG seq=4 rtt=0.379 ms
PONG seq=5 rtt=0.401 ms
--- ping statistics ---
sent=5 received=4 loss=20.0%
rtt min/avg/max = 0.379/0.395/0.412 ms
```

در این خروجی، از ۵ بسته ارسال‌شده، ۴ بسته پاسخ دریافت کرده‌اند و یک بسته با Timeout مواجه شده است. در نتیجه، میزان اتلاف بسته‌ها برابر با ۲۰ درصد خواهد بود.

### ۴.۲. سناریو دوم: بررسی عملکرد کلاینت در شرایط اتلاف کامل بسته‌ها

در این سناریو، احتمال اتلاف بسته‌ها روی ۱۰۰ درصد تنظیم می‌شود تا هیچ پاسخی از طرف سرور به کلاینت نرسد.

هدف این تست، بررسی عملکرد کلاینت در شرایطی است که تمام درخواست‌ها با Timeout مواجه می‌شوند و همچنین اطمینان از محاسبه صحیح آمار در پایان اجرا است.

**دستور اجرا در قاب سرور:**

```bash
./ping-server --port 9000 --loss 1.0
```

**دستور اجرا در قاب کلاینت:**

```bash
./ping-client --host 127.0.0.1 --port 9000 --count 3 --timeout 500
```

**نمونه خروجی مورد انتظار کلاینت:**

```text
TIMEOUT seq=1
TIMEOUT seq=2
TIMEOUT seq=3
--- ping statistics ---
sent=3 received=0 loss=100.0%
rtt min/avg/max = -/-/- ms
```

همان‌طور که مشاهده می‌شود، هر سه درخواست با Timeout مواجه شده‌اند و چون هیچ پاسخی دریافت نشده است، مقادیر مربوط به حداقل، میانگین و حداکثر RTT با علامت `-` نمایش داده می‌شوند.

### ۴.۳. سناریو سوم: بررسی مدیریت پیام‌های نامعتبر با Netcat

در این سناریو، نحوه برخورد سرور با پیام‌هایی که قالب درستی ندارند بررسی می‌شود.

برای انجام تست، ابتدا سرور را اجرا کنید. سپس در قاب کلاینت، دستور زیر را با استفاده از ابزار `nc` وارد کنید:

**دستور اجرا در قاب کلاینت:**

```bash
echo "INVALID_MSG 123" | nc -u -w1 127.0.0.1 9000
```

**خروجی مورد انتظار:**

```text
ERR BAD_REQUEST
```

در صورت دریافت یک پیام با قالب نامعتبر، سرور باید پیام خطای `ERR BAD_REQUEST` را برگرداند.

نکته مهم این است که پاسخ به پیام‌های نامعتبر تحت تأثیر احتمال اتلاف بسته قرار نمی‌گیرد؛ بنابراین حتی در صورت فعال بودن مکانیزم `Packet Loss`، سرور باید پاسخ خطا را ارسال کند.

## ۵. ابزارها و فناوری‌های استفاده‌شده

در پیاده‌سازی این بخش از پروژه، از ابزارها و فناوری‌های زیر استفاده شده است:

| ابزار / فناوری | کاربرد |
|:---|:---|
| `C++11` | زبان برنامه‌نویسی مورد استفاده برای پیاده‌سازی |
| `UDP Sockets` | برقراری ارتباط میان سرور و کلاینت |
| `select` | بررسی وضعیت سوکت و مدیریت زمان انتظار بدون مسدود شدن برنامه |
| `steady_clock` | اندازه‌گیری زمان و مدیریت زمان‌بندی ارسال بسته‌ها |
| `Makefile` | ساده‌سازی فرایند کامپایل و اجرای دستورات مورد نیاز |
| `Tmux` | اجرای هم‌زمان سرور و کلاینت در دو قاب جداگانه |
| `Netcat (nc)` | ارسال پیام‌های آزمایشی و بررسی نحوه برخورد سرور با پیام‌های نامعتبر |

## ۶. نحوه استفاده از هوش مصنوعی

در انجام این بخش از پروژه، مطابق الزامات صورت پروژه، از دستیار هوش مصنوعی صرفاً در موارد زیر کمک گرفته شده است:

- طراحی اولیه ساختار ماژولار کلاس‌ها و تقسیم وظایف میان آن‌ها در فایل‌های Header.
- راهنمایی درباره نحوه استفاده از تابع `select` برای مدیریت Timeout و جلوگیری از مسدود شدن سوکت کلاینت.
- کمک به تنظیم و ساختاربندی فایل `Makefile` برای ساده‌تر شدن فرایند کامپایل و ایجاد محیط تست با استفاده از `Tmux`.
